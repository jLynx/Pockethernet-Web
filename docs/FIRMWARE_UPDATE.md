# Browser firmware updates

In **Tools → Device info**, connect Pockethernet and select **Check for upgrade → Update → Start update**. An available update appears as one banner with its version and Update action. Use an Internet-connected Ethernet switch with DHCP, keep the device powered on, and keep Pocketweb open. Turn off the toner, blinker and WiFi bridge first.

Pocketweb sends the official ESP update URL over Bluetooth. The device downloads and validates the firmware over Ethernet. It reports a final result, rather than download percentages. After success, unplug USB, turn the device off, wait five seconds and turn it on again. Select **I have restarted · verify firmware** and connect the same Pockethernet. Pocketweb checks the ESP version and confirms the STM version is unchanged.

The regular flow installs official ESP firmware. On our custom ESP v16, updating to official v17 replaces the custom application.

## Advanced updates

**Shift-click Check for upgrade** (or **Update** when an update is already available) to install a custom URL or OTA file. This developer shortcut has no visible button or tooltip in the normal UI. This mode permits same-version installations and downgrades. Review the source and expected ESP version before selecting **Start update**.

- **Custom URL:** enter a direct HTTP(S) URL reachable from the device's Ethernet port, plus the ESP version the image will report after boot. URLs are limited to 60 ASCII bytes. No browser cookies, credentials or client certificates are forwarded. A LAN URL such as `http://192.168.1.161:8765/fw.bin` is supported.
- **OTA file:** choose a packaged **PEUI ESP OTA container** such as `pen_e_custom_experimental_16_*.bin` or official `pen_e_crypt_17.bin`. Raw PlatformIO `firmware.bin`, full USB dumps, and STM packages are unsupported. The browser reads the container's ESP version, size and SHA-256; the device still performs authentication, decryption and image validation.
- **Hosting:** selecting a file only inspects it. **Upload and start update** uploads it to Pocketweb and creates an immutable random download link, available to anyone with that link for 30 minutes. Files are capped at 4 MiB and automatically deleted on expiry. No file bytes are sent over Bluetooth. Uploaded bytes and metadata are compared before F401 is allowed.
- **Same-version verification:** a successful status 10 followed by your confirmed restart and matching version does not identify the build when old and new images report the same number. The UI says so. If the OTA result was lost, that same-version outcome remains unconfirmed rather than being labelled verified.

The Cloudflare deployment needs the `OTA_FILES` SQLite Durable Object binding and migration supplied in `wrangler.toml`; the next deployment creates it. A Vite-only server cannot host device downloads by itself. For local development, run `npx wrangler dev --local --ip 0.0.0.0 --port 8787` alongside Vite. Vite proxies the upload/download routes to that Worker. Set **Download host** to its reachable LAN origin, for example `http://192.168.1.161:8787`. Browser `localhost` refers to the PC; device `localhost` refers to Pockethernet, so it cannot be used as the download host.

## Compatibility contracts and refactoring gotchas

- Reference: `android-reference/com.pockethernet.android.pe2/java_src/com/pockethernet/android/pe2/pe_ota_pen.java` and `protocol_pen.java`; same-device recovery evidence is in `firmware-local/esp32-service/results/`.
- The command is **F401 (ESP update)**. Never send F400, which updates STM. Firmware bytes are not written over Bluetooth.
- F401 payload: little-endian uint16 timeout of 300 seconds, uint8 URL length including its terminating NUL, then ASCII URL and NUL. Keep the stock-compatible maximum of 60 URL bytes, even though our remake has a larger buffer.
- The latest-version endpoint returns `version#url`. Version comparison uses the ESP version, not the combined ESP.STM display. The regular check accepts only official HTTPS `ota.pockethernet.com/pen_e_crypt_VERSION.bin` URLs and offers newer versions. Only the explicit advanced flow permits other URLs, reinstalls and downgrades. Both paths forbid URL credentials and fragments, and retain the same device identity/network/F401 checks.
- Uploaded containers must identify image type **2 (ESP)** and contain an exact 128-byte-header-plus-body length. Header inspection is structural, not cryptographic authentication. Do not claim that a browser SHA-256 or PEUI magic check authenticates a firmware package. Stock/custom receiver checks remain authoritative.
- Cloudflare Workers drops a manually supplied Content-Length on an unknown-length ReadableStream. Serve a bounded ArrayBuffer (maximum 4 MiB) so the actual HTTP runtime preserves the length. Content-Encoding must remain identity and bytes must not be compressed or transformed. Durable Object chunks stay below its 128 KiB value limit; downloads reassemble the original bytes in order.
- Random `/f/` links use 16 random bytes encoded into 22 base64url characters, leaving the production URL within the stock 60-byte limit. Uploads are same-origin only. Do not shorten links by reducing token entropy, overwrite a stored link, delete it during an uncertain OTA, or proxy arbitrary custom URLs through the backend. Expiry is enforced on reads as well as by an alarm.
- The APK uses Ethernet interface flags 9, IP flags 3, PHY flags 1773: 10/100 with DHCP, factory MAC and untagged Ethernet. OTA must not inherit measurement VLAN, static-IP or discovery settings.
- Register both link-up and DHCP listeners **before** ETH_CONFIG. Notifications can arrive before its ACK, and DHCP can arrive before link-up. Passive listeners must not consume a command NACK. The link deadline starts after configuration ACK; the DHCP deadline starts after link-up. Link-down notifications are ignored while establishing the link.
- Wait **10 seconds after DHCP ACK** before F401. Stock forwards that packet before activating its lwIP address. Removing this delay reproduced stock download failures during the earlier hardware investigation.
- F401 replies with exactly four bytes, a little-endian uint32 status. Only **10** means download/validation/boot-slot selection succeeded. It does not restart the device or prove that the new version has booted.
- The progress indicator is indeterminate: the protocol provides no download percentage. Its CSS animation moves only a transform, without JavaScript timers or changing layout each frame. Keep the same indicator mounted between active stages so motion continues smoothly. Reduced-motion settings use a static segment; do not add a made-up percentage or `aria-valuenow`.
- Known failures: 1 no partition; 3 download-client setup; 11 connection/header; 12 authentication/image validation; 13 flash write/slot capacity; 14 interrupted body; 15 final verification; 16 boot-slot selection. Include the numeric code in the UI.
- **0**, **255**, malformed replies, unknown codes, a Bluetooth write error, disconnect or timeout after the command starts have an uncertain outcome. In particular, 255 means the worker may continue independently, without a later completion reply. Never retry automatically or stop Ethernet in these cases. Wait for the caller deadline, restart the device, and verify first.
- The UI waits 310 seconds for the final response, covering the device's 300-second caller timeout. Its verification action remains blocked until this deadline for uncertain outcomes. Clicking that action explicitly confirms that the user has restarted the device; the protocol has no boot counter with which to independently establish a power cycle.
- Store the pending device identity, target and start time **before** attempting F401. A reload or closed tab must recover as uncertain, rather than enable another update. If storage cannot be written, stop before sending F401. The marker never authorizes a resumed download.
- Stop Ethernet after a known completed worker result, or failure before starting OTA, as the APK does. A missing cleanup ACK must not override a successful OTA status. Cancel all passive listeners on exit.
- Exclude measurement/tool commands and battery polling while installing and until restart verification. Tool writes already in flight also block OTA preflight. Disable the deliberate Bluetooth disconnect button during the operation; a physical disconnect is still possible.
- Re-read device info immediately before configuration, and verify device serial/MAC/hardware identity again after restart. The serial alone can be a factory fallback; it must not identify an update target on its own. Verify the exact requested ESP version and the unchanged STM version. An unexpected version or different device must not be labelled verified.
- There is no request sequence number in the original protocol. Late packets from earlier operations cannot always be distinguished. Controlled command ordering, exclusive operation ownership and canceling waiters reduce that risk; they do not add a protocol correlation ID.

## Validation

`npm test` includes the real packet-inbox regression suite for exact F401 bytes, official/custom URL validation, reverse/early notifications, configuration flags, DHCP settling, duplicate clicks, all documented result codes, transport failures, malformed replies, timeout, cleanup, blocked tools/measurements, storage failure, reload recovery, wrong-device/version checks and unchanged STM verification. Advanced tests cover reinstalls/downgrades, same-version ambiguity, file inspection without upload, upload integrity, failure before F401 and recovered file metadata. Hosting tests cover immutable links, expiry, request methods and exact bytes. A real Miniflare Workers HTTP/SQLite test serves 1,276,736 synthetic bytes and checks Content-Length; this catches behavior a Node Response fixture cannot reproduce. Display tests and Storybook states cover availability, advanced forms, confirmation, indeterminate progress, errors, restart and uncertain outcomes.

These are offline tests. The direct Ethernet downloader and stock/custom restoration were hardware-tested earlier through the local Python OTA tools. The newly implemented browser flow still needs an explicitly started end-to-end device update. No device is flashed by the automated tests.

Suggested live acceptance check: update custom ESP v16 to official v17 from Pocketweb on an untagged DHCP LAN; receive status 10; power-cycle; verify the same device reports ESP 17 and unchanged STM 17; run a normal measurement afterward. Network-loss tests during a real flash require a recovery route and are separate from the offline regression gate.
